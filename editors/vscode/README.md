# SplitScript for Visual Studio Code

This extension associates `.split` files with SplitScript and runs the Rust
language server from compiler WebAssembly bundled in the extension. Formatting,
diagnostics, completion, hover, signature help, semantic highlighting,
navigation, rename, document symbols, and quick fixes are provided by the same
compiler implementation as native `splitls`.

## Build workflows

The extension exposes two explicit workflows from the editor title, context
menu, and Command Palette:

- **SplitScript: Start Debug Watch** starts the bundled compiler in an isolated
  worker using the debug profile. It compiles immediately and recompiles the
  neighboring `.wasm` whenever the source file is saved. A status-bar indicator
  remains visible and can be clicked to stop the watcher.
- **SplitScript: Build Release** performs a one-shot release build intended for
  the final module. It saves pending edits, reports progress, and offers to
  reveal the resulting `.wasm` file.

Starting a release build while debug watch is active first offers to stop the
watcher, preventing a later debug rebuild from overwriting the release module.
Both workflows report to **SplitScript Compiler**. Failed and superseded builds
preserve the last successful Wasm module. Compilation runs from source snapshots
tagged with the exact VS Code document revision, and generated bytes are written
through the VS Code workspace filesystem. No separately installed `splitc`
executable or compiler-path setting is used.

## Bundled language server

The client gives the language server its own worker and Wasm instance, separate
from the build worker. No native executable, platform-specific package, or
server setting is required. **SplitScript: Restart Language Server** replaces
that worker with a fresh instance. Native `splitls` remains available from the
repository root for other editors and command-line LSP clients.

The manifest provides both desktop and browser entries. The browser entry uses
`vscode-languageclient/browser` and dedicated browser workers for compilation
and LSP traffic; its extension code is bundled into one file as required by the
web extension host. Workspace and extension files are accessed only through
VS Code URIs and `workspace.fs`, including in virtual workspaces.

## Documentation

**SplitScript: Open Documentation** opens the compiler-owned reference beside
the current script. It includes the language, lifecycle blocks, migration
guidance, the ASL porting guide, and the standard library in one searchable,
hierarchical graph. Migration diagnostics link to the exact corresponding
page. **SplitScript: Search Documentation** searches every page by symbol,
concept, kind, signature, and summary without requiring repository files.
Catalog-backed hover and completion details link directly to the corresponding
full page, and go-to-definition on language or standard-library symbols opens
that same virtual document. The client trusts only the documentation-opening
command in language-server Markdown; unrelated command links remain disabled.

## Development

From this directory:

```console
npm install
npm run check
npm run compile
```

`npm run compile` builds the optimized `wasm32-unknown-unknown` compiler adapter,
compiles the TypeScript extension and its language/build workers, and copies the
compiler module into the ignored `dist` package directory. Native `splitc` and
`splitls` builds remain available independently from the repository root.

`npm run test:web-host` launches the bundled browser entry headlessly in a real
Chromium VS Code web host with a virtual workspace. It verifies language-server
startup and restart, hover, release compilation, debug watch, virtual-file
writes, and recompilation after a save. The first run downloads the pinned VS
Code web test build into the ignored `.vscode-test-web` cache.

To explore that browser environment interactively, build the extension and open
the same sample workspace without the test runner:

```console
npm run compile
npm run open:web-host
```

The browser remains open until it is closed or the command is stopped. Files in
this test workspace use an in-memory virtual filesystem, so edits made there do
not modify the checked-in `test-workspace` files.

When the full repository is open in VS Code, the checked-in **Run SplitScript
Extension** launch configuration compiles the WebAssembly adapter and TypeScript
client before opening an Extension Development Host. **Run SplitScript Web
Extension** starts the same package in VS Code's browser extension host.
